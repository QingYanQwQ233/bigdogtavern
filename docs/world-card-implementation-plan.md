## 1. 任务边界

### 目标

把现有“角色卡 + `kind: rpg` 会话”逐步替换为以下两个互不串数据的闭环：

```text
酒馆：角色卡 → ChatSession → 酒馆 Prompt → 对话历史
世界：WorldCard → WorldSave → 世界 Prompt → 回合 / 状态 / 地图 / NPC
```

最终必须证明：玩家进入世界、创建存档、完成一回合、保存、退出、重开后，叙事、数值、任务、地图、图片和 NPC 状态一致恢复；切换世界、存档、角色或模式时不会串数据。

### 不可违反的不变量

1. 世界定义只由 `worldId + worldVersion` 定位；可变化事实只由 `saveId + revision` 定位。
2. 酒馆会话只由 `charId + chatSessionId` 定位；世界模式不从 `currentCharId` 或全局 `mode` 推断存档归属。
3. AI 输出先形成候选变化，校验并耐久保存成功后才成为正式事实。
4. 地图数据、AI 美化图路径、行动选项、任务、背包和 NPC 动态状态全部属于一个 `WorldSave`。
5. 旧 RPG 会话在迁移阶段前只读保留；迁移失败或取消不能覆盖、合并或删除原数据。
6. 服务端只接受受控 ID，不接受客户端文件路径；导入的 HTML、EJS、MVU、正则脚本和 JavaScript 默认不执行。
7. `_defaults.json` 仍是模板种子的唯一来源；前端不写死世界内容、角色内容或默认数值。

### 当前证据与约束

- `public/app.js` 仍是单文件，但 W2 已通过 `worldModeActive()` 把世界模式的时间线、状态、地图和图片路径切到当前 `WorldSave`。
- 旧 RPG 会话仍使用 `session.rpgState` 与 `localStorage`，新世界存档不读取或改写该路径。
- `server.js` 已增加按 `saveId` 的 `PUT`、`expectedRevision` CAS、原子 JSON 写入与地图图片路径 / 网格校验；完整回合事务与幂等 receipt 留给 W3。
- Android 的 `TavernServer.kt` 复制了数据 API，Web 端接口稳定后必须单独补齐，不能假定自动兼容。
- 项目零 npm 依赖；实施优先使用浏览器能力与 Node 标准库，不引入数据库、框架或状态管理库。
- 只做本地 commit，不 push；本阶段只修改新 WorldSave 主链，不自动迁移旧 RPG 数据。

## 2. 阶段依赖

```text
W0 设计闭合与基线
  ↓
W1 世界库 + 新建 / 打开存档
  ↓
W2 WorldSave 范围内的时间线 / 状态 / 地图
  ↓
W3 回合候选校验 + revision 原子提交
  ↓
W4 NPC / 队伍 / 地点 / 世界书作用域
  ↓
W5 世界卡编辑 / 版本 / 世界包
  ↓
W6 旧 RPG 会话迁移
  ↓
W7 Web / PWA / Android 收口与交付
```

W1–W3 必须串行，因为它们同时改变正式状态 owner 和 `public/app.js` 的主调用链。W4 以后也只在上一阶段通过恢复与隔离验收后开始，避免在错误的数据边界上继续堆功能。

## 4. W0 — 设计闭合与可回滚基线

按“一个决定单元一轮”确认，不把用户未回答视为同意：

1. 玩家角色：默认自建、世界预设主角，或两者都允许但指定默认值。
2. 控制权：单主角，或允许在队伍成员间切换控制。
3. 模式名称：继续叫“RPG”，或改为“世界”。
4. 入口：直接进入世界桌面，或先经过可选角色 / 开场页。

产物：回写架构文档“已确定 / 暂定 / 待讨论”状态，并记录对 Schema、Prompt 和 UI 的影响。

### W0.2 冻结第一版契约

- 确认 `WorldCard.schemaVersion = 1`、`WorldSave.schemaVersion = 1` 和 RPG 输出协议版本。
- 登记每个正式字段的 owner、创建者、修改者、读取者、默认值、持久化和无效值处理。
- 明确地图序列化格式：JSON 中 `grid` 是数字数组，运行时恢复为 `Uint16Array`。
- 明确图片只保存本地相对路径，不把 base64 塞入世界存档。
- 明确删除语义：第一阶段不提供删世界 / 删存档，避免先实现不可恢复操作。

## 5. W1 — 世界库与新存档最小闭环（当前第一实施阶段）

### 目标体验

用户切换到世界模式，看到来自 JSON 的世界卡列表；选择一个世界并输入存档名后创建新存档；刷新页面后仍能从该世界的存档列表重新打开。此阶段只证明“世界卡 → 世界存档”的归属与耐久保存，不接 AI 回合。

### 非目标

- 不迁移旧 `kind: 'rpg'` 会话。
- 不改 `processAIOutput()`、掷骰或 Prompt 管线。
- 不做世界编辑器、存档删除、分支、云同步或 Android 接口。
- 不重写 `app.js` 为模块系统，也不引入 npm 依赖。

### W1.1 数据种子与 Schema

涉及：`public/data/_defaults.json`、`public/data/worlds.json`（运行时文件，继续忽略 Git）、`.gitignore`、架构文档。

- 在 `_defaults.json` 新增最小 `worlds` 段，放一个测试世界；世界内容和初始数值不写入 JS。
- 将 `public/data/saves/` 明确加入 `.gitignore`，防止玩家存档、叙事和本地图片引用进入提交。
- 世界卡必须有稳定 `id`、`version`、`title`、开局地点和 RPG 预设引用。
- 新存档必须有 `id`、`worldId`、`worldVersion`、`revision = 0`、玩家快照、初始状态、空回合和空 receipts。
- 增加只用 Node `assert` 的 Schema 自检，覆盖缺 ID、未知世界、重复存档 ID 和无效 revision。

完成证据：合法样例通过；四类无效样例被拒绝。

### W1.2 Node 存储 API

涉及：`server.js`、`public/data/saves/`、对应检查脚本。

最小接口：

```text
GET  /api/worlds
GET  /api/world-saves?worldId=<worldId>
POST /api/world-saves
GET  /api/world-saves/<saveId>
```

- `/api/worlds` 从 `worlds.json` 读取；W1 不开放世界卡写接口。
- 存档列表扫描 `saves/*.json` 的顶层元数据，不创建第二份权威索引。
- 静态文件服务拒绝直接读取 `/data/` 下的运行时 JSON；浏览器只能通过受校验的 API 访问。
- `POST` 只接受声明字段，校验 `worldId/worldVersion` 后由服务端分配 `saveId` 和时间戳。
- `saveId` 经过固定格式校验并由服务端映射到目录；任何斜杠、反斜杠、点路径或绝对路径都拒绝。
- 创建采用同目录临时文件 + 替换；失败删除临时文件并返回结构化错误，不留下半个 JSON。
- 为本地单用户写入串行化；若采用全局写锁，代码标明“数百存档以内”的上限，实测需要并发时再升级为按存档锁。

完成证据：创建两个存档、重启 `server.js`、按世界列出并分别读取；路径穿越与重复 ID 请求失败。

### W1.3 前端世界状态入口

涉及：`public/app.js`。

- 新增独立的 `worldCards`、`currentWorldId`、`currentWorldSaveId` 和当前 `WorldSave` 内存状态。
- `localStorage` 只保存最近打开的世界 / 存档 ID 和可重建列表缓存，不保存正式世界状态。
- 增加 `loadWorlds()`、`listWorldSaves(worldId)`、`createWorldSave()`、`openWorldSave(saveId)` 和 `curWorldSave()`。
- 世界路径不能调用 `sessionMatches()`、`getGreeting()` 或从 `currentCharId` 推断归属。
- 酒馆 `sessions` 原样保留；当前 RPG 会话数据也不删除、不改名、不自动转换。

完成证据：切换角色或酒馆会话不会改变当前世界存档；切回世界模式仍打开原 `saveId`。

### W1.4 最小世界库 UI

涉及：`public/index.html`、`public/styles.css`、`public/app.js`。

- 复用现有导航、卡片、按钮、弹窗和 CSS 变量；不在 W1 定稿完整世界桌面视觉。
- 世界卡显示标题、摘要、版本和存档数；提供“新建存档”和“打开”两个动作。
- 新建表单具备明确 label、键盘操作、加载状态、错误提示和重复提交保护。
- 没有世界、没有存档和服务器不可用时分别显示可理解的空状态。
- UI 只发 Command / API 请求，成功响应后再更新当前存档投影。

完成证据：用真实浏览器完成“进入世界库 → 新建 → 刷新 → 打开”，并检查窄屏与键盘焦点。

### W1.5 回归与交付

- 新增 `scripts/check_world_storage.js`，覆盖创建、列表、重启恢复和路径边界。
- 现有 `check_session_binding.js` 必须继续通过，证明旧酒馆 / RPG 会话未被 W1 破坏。
- 更新 `docs/data-structure.md`，把“当前实现”与“世界卡目标实现”分开描述，不能把未完成阶段写成已上线。
- W1 单独本地 commit；不 push。

本次 W1 证据：`scripts/check_world_storage.js` 通过创建、列表、重启恢复和路径边界检查；既有三条 Node 检查、三个语法检查通过；真实浏览器完成进入 RPG 世界库、分别用点击与回车创建两个存档、刷新后恢复列表与打开状态，控制台无错误。

W1 的刻意边界：世界库目前是独立入口，不会拦截或改写旧 RPG `sessions`；“回到旧 RPG 对话”是兼容出口。W2 才把当前世界存档接入叙事栏、状态、地图和图片。

### W1 失败语义与回退

| 失败 | 数据结果 | 用户反馈 | 恢复 / 回退 |
|---|---|---|---|
| 世界列表读取失败 | 不创建或覆盖任何存档 | 世界库显示服务不可用 | 重试 GET；酒馆仍可用 |
| 新建请求校验失败 | 无文件产生 | 表单保留输入并指出字段 | 修正后使用新请求重试 |
| 写文件中断 | 正式目标文件保持旧状态或不存在 | 显示创建失败 | 清理临时文件；从 W1 基线 commit 回退 |
| 最近存档 ID 已失效 | 不猜测其他存档 | 回到该世界存档列表 | 用户显式选择 |

### W1 完成定义

以下项目全部通过才进入 W2：

1. 同一世界创建两个存档，ID、名称和文件互相独立。
2. 两个世界的存档列表互不出现对方内容。
3. 服务重启、页面刷新后可恢复打开。
4. 切换酒馆角色 / 会话不改变当前世界存档。
5. 无效 ID 和路径穿越不能读写文件。
6. 在完成现有初始化后取快照；运行 W1 新功能前后，旧 `sessions`、角色卡、世界书、预设和地图数据保持不变。
7. Node 静态检查、目标脚本和真实浏览器流程均有记录。

## 6. W2 — WorldSave 范围内的叙事、状态与地图

### 分步任务

- **W2.1 时间线投影**：世界模式从 `WorldSave.turns` 和开局叙事渲染；酒馆继续读取 `ChatSession.messages`。世界模式不复用角色开场白兜底链。
- **W2.2 状态投影**：`renderRPG()` 改为显式接收或读取当前 `WorldSave.state`；HP、MP、金币、任务和背包的手动操作只提交当前 `saveId`。
- **W2.3 地图序列化**：在 `mapgen.js` 提供最小 serialize / hydrate 边界，JSON 网格与运行时 `Uint16Array` 往返一致。
- **W2.4 地图归属**：`curMapData()`、重新生成、点击命中、地图 JSON 和上下文构造只读取当前存档地图；不再通过 `curRpgState()` 找会话。
- **W2.5 美化图归属**：生图成功后只把相对路径写入当前 `WorldSave.state.map.imagePath`；切换存档时图片同步切换，迟到响应不得写入新存档。
- **W2.6 保存入口统一**：所有世界状态的非 AI 修改走一个带 `expectedRevision` 的保存入口；成功 ACK 后才刷新正式投影。
- **W2.7 隔离回归**：同世界双存档、不同世界双存档分别修改地图、任务、背包和图片，断言其他存档不变。

当前实现证据：`scripts/check_world_storage.js` 覆盖双世界 / 双存档、PUT CAS、地图网格序列化、图片路径校验和重启读取；Playwright 已确认“创建两个世界存档 → 进入工作区 → 修改一个存档背包 → 切换存档后另一份为空”的真实页面流，控制台无错误。

完成门：关闭页面并重开后，四类状态一致；一次保存失败时服务端 revision 不前进，界面显示未保存警告；旧 `sessions` 不被世界路径写入。

## 7. W3 — 世界回合事务与 RPG 输出协议

### 分步任务

- **W3.1 命令模型**：一次输入创建稳定 `commandId`、`saveId` 和 `expectedRevision`；发送期间切换存档不会改变目标。
- **W3.2 待提交输入**：玩家输入、掷骰结果和流式正文先放在 pending overlay，不提前追加到正式 `turns`。
- **W3.3 Prompt 装配**：新增显式 `buildWorldPrompt(worldCard, worldSave, command)` 路径；酒馆继续使用角色卡路径。最终仍只发送一条 system。
- **W3.4 输出解码**：`splitRpgOutput()` 只负责叙事与 `rpg` 块边界；v3 解码器把 JSON 变成 `CandidateTurn`，不直接写状态。
- **W3.5 候选校验**：检查协议版本、恰好四个选项、数值边界、稳定地点 / NPC / 物品 / 任务 ID、允许创建的实体类型和玩家主权；当前 Web 切片已先落地状态数值、背包、任务和地图数组的服务端边界。
- **W3.6 事务提交**：服务端在同一临界区检查 revision 和 receipt，再一次写入 turn、state、revision 与 command receipt；当前 Web 切片已落地，NPC 状态与临时实体由 W4 实体边界继续约束。
- **W3.7 幂等与对账**：相同 `commandId` 返回原提交结果；保存结果未知时先查询 receipt，禁止直接重放模型请求。
- **W3.8 错误恢复**：模型、流式、解析、校验、冲突和写入错误分别显示；当前 Web 切片已让失败 pending 保留玩家输入并提供“重试 AI / 放弃本回合”，重试复用同一 `commandId`，但完整候选复制 / 分类型错误面板仍待补。
- **W3.9 调试 Trace**：独立终端按 `saveId + commandId` 显示输入块、原始输出、候选变化、校验结果和提交 ACK；不把 API key 或完整 Trace 写进存档。

最小验证矩阵：成功一回合；无 `rpg` 块；坏 JSON；无效地点；五个选项；保存冲突；相同命令重试；响应期间切换存档；重启后对账。只有成功路径增加 revision。

## 8. W4 — 多 NPC、队伍、地点与世界书作用域

### 分步任务

- **W4.1 玩家 / 队伍**：玩家模板在建档时形成快照；世界存档只保存成员动态状态，角色库后续编辑不静默改旧存档。当前 Web 切片已形成玩家快照和 `party` 容器，队伍 UI / 成员切换仍待补。
- **W4.2 NPC 双层模型**：世界卡保存 NPC 静态定义，`WorldSave.npcStates[npcId]` 保存关系、位置、认知和状态。当前 Web 切片已按 `npcIds` / `npcs` 初始化独立 `npcStates`，回合提交可携带并校验它；尚未注入 Prompt 作用域。
- **W4.3 地点 ID**：所有位置写入稳定 `locationId`；旧的自由文本只用于迁移兼容，不再作为正式关联键。当前 Web 切片已在建档、普通存档提交和回合提交时校验 `state.locationId` / `npcStates[*].locationId` 属于固定世界版本，并在 RPG Prompt 中明确位置协议。
- **W4.4 作用域选择**：Prompt 只注入队伍成员、当前地点 NPC、当前任务相关 NPC 和关键词命中的世界书，不注入世界全部角色。当前 Web 切片已按 `party.memberIds`、`state.locationId`、`npcStates[*].locationId` 和任务中的 NPC 引用确定性筛选，并为每个选中 NPC 合并静态定义与当前存档动态状态。
- **W4.5 认知边界**：NPC 只能读取世界公共知识、其定义允许且已解锁的秘密和本存档已获知事实；跨存档记忆绝不进入 Prompt。当前 Web 切片采用公开字段白名单，`secrets` 只有被当前 `npcStates[npcId].knowledge` 持有对应 ID 时才注入，并明确禁止臆测未注入秘密。
- **W4.6 开放生成**：AI 只能提出 `createEntities`；校验器生成 `save:*` ID 并写入当前存档的 `generatedEntities`。当前 Web 切片支持 NPC / 道具 / 任务 / 地点四类候选，限制数量与字段大小，生成 ID 不接受模型自带 ID，并让当前存档的生成 NPC 继续按地点作用域进入 Prompt。
- **W4.7 收录到世界**：已实现 `POST /api/worlds/<worldId>/versions`。命令校验来源存档、revision 和 `save:<saveId>:npc:<n>` 所有权，复制来源世界卡并创建下一版本，分配新的稳定 NPC ID；重复收录幂等，旧世界版本和旧存档保持不变。客户端打开存档时按 `worldId + worldVersion` 拉取精确世界卡，避免新版本串入旧存档。
- **W4.8 Trace 验证**：已用回归脚本构造两个世界、两个存档、同名 NPC 和同关键词世界书；断言静态 NPC、存档生成 NPC 与世界书条目均只进入所属 Prompt，且全局世界书选择不会覆盖 WorldCard 绑定。

当前切片完成门：同一世界的两个存档各自拥有独立玩家快照、NPC 状态、稳定地点引用和生成实体；服务端重启后仍能恢复。完整完成门仍为：同一 NPC 在两个存档可有不同关系和位置；同名实体仍按 ID 正确归属；生成实体只在创建它的存档可见。

## 9. W5 — 世界卡编辑、版本与世界包

### 分步任务

- **W5.1 世界编辑入口**：已实现世界库的“创建世界草稿 / 编辑草稿”入口。草稿独立保存到 `world-drafts.json`，使用 `expectedUpdatedAt` 乐观锁；保存不会原地修改已发布世界卡。
- **W5.2 声明式地点与 NPC 编辑**：已实现地点/NPC 结构化编辑、稳定 ID、地点引用校验、NPC 秘密字段保留与白名单归一化；仍不允许在草稿中执行 HTML/JS。
- **W5.2 后续声明式字段**：继续补齐开局、RPG Profile、物品 / 任务模板等纯数据字段；不接受可执行 HTML / JS。
- **W5.3 地图参数**：已把 `seed`、`size`、`regionCount`、`landRatio`、`mapgenSize` 接入世界草稿与可视化预览；服务端限制安全范围，地图生成与重生成读取存档所绑定世界版本的配置。
- **W5.4 发布版本**：已实现草稿发布为不可变 `worldVersion + 1`；使用 `commandId` 幂等重试、基础版本冲突校验与发布来源记录，旧版本和旧存档继续读取原版本。
- **W5.5 存档升级**：已实现显式选择更高版本、地点/NPC/任务引用 dry-run、硬错误阻断、revision 复核、幂等提交与 `migrationHistory`；新增世界 NPC 只初始化当前存档的状态。
- **W5.6 世界包导出**：已实现版本化 JSON 世界包，包含世界定义、精确引用的角色 / 世界书 / 预设、资源清单、来源、作者/许可占位和确定性 SHA-256；服务端剔除凭据、本机路径、来源存档 ID，且不包含玩家存档。
- **W5.7 世界包导入**：已实现原件只读封存、`contentHash`/引用/资源/私密字段预演、未知 sidecar 的“保留但未执行”报告，以及确认后的专属 ID 映射。失败包不进入世界库，重复确认幂等。
- **W5.8 UI 验证**：实施时使用 `frontend-design`、`web-interface-guidelines` 和真实浏览器检查桌面 / 窄屏、键盘、焦点、错误与 reduced motion。

完成门：发布 v2 后，v1 存档重开仍使用 v1；升级只有在用户确认且 dry-run 无硬错误时发生。

## 10. W6 — 旧 RPG 会话迁移

### 分步任务

- **W6.1 只读盘点**：读取 `localStorage` 旧 sessions，生成会话数、角色归属、状态、地图、图片和异常字段报告，不写任何数据。
- **W6.2 原始备份**：允许下载完整原始 JSON，并记录来源哈希、Schema 推断和迁移批次 ID。
- **W6.3 映射预演**：默认每个 `kind: 'rpg'` 会话映射为一个 `WorldSave`；`charId` 只创建玩家快照，不作为世界 / 存档主键。
- **W6.4 世界归属选择**：无法可靠判断的会话由用户选择目标世界；不自动合并，不自动创建含糊的共享世界。
- **W6.5 数据转换**：消息转已提交时间线，`rpgState` 转 state，地图网格显式序列化，`mapImage` 转相对路径引用，旧 options 绑定到对应回合。
- **W6.6 小样本执行**：先迁一个副本并重开验证；成功后再逐个执行，其余会话失败不回滚已成功项，也不删除原件。
- **W6.7 幂等重试**：迁移批次和源会话 ID 写入 migrationHistory；重复执行返回既有目标，不创建第二份存档。
- **W6.8 兼容退路**：迁移完成后旧 RPG 会话仍保留只读入口，直到用户明确确认清理；本阶段不自动删除。

完成门：正常、缺 charId、坏地图、缺图片、重复迁移和中途失败六类样本均有报告；原始 localStorage 可恢复。

## 12. 每阶段固定检查

### 静态与脚本

```powershell
node --check public/app.js
node --check public/mapgen.js
node --check server.js
node scripts/check_character_fields.js
node scripts/check_prompt_presets.js
node scripts/check_session_binding.js
node scripts/check_recovery.js
node scripts/check_pwa.js
```

阶段新增的 `scripts/check_world_*.js` 必须使用 Node 标准库即可运行。涉及浏览器表面时，再用 Playwright 验证真实流程；涉及失败时先复现根因，再修复并留下最小回归检查。

### 数据隔离断言

每个阶段至少重复以下矩阵中与其相关的部分：

| 操作 | 必须变化 | 必须不变 |
|---|---|---|
| 切换酒馆角色 | 该角色的 ChatSession 投影 | 所有 WorldSave |
| 切换世界存档 | 当前时间线、状态、地图、图片 | 其他 WorldSave、所有 ChatSession |
| 提交世界回合 | 目标 `saveId` 的 revision 与事实 | 世界卡、其他存档、角色卡 |
| 编辑世界草稿 | 草稿版本 | 已发布版本和已存在存档 |
| 发布世界草稿 | 追加不可变世界版本并消费草稿 | 旧世界版本与已有存档的 `worldVersion` |
| 迁移旧会话 | 新建目标存档和迁移报告 | 原始旧会话 |

### 阶段交付格式

每阶段结束只报告可证明的内容：

- 修改文件和行为；
- 通过 / 失败 / 仅 Mock / 未验证的检查；
- 数据备份与回退点；
- 未解决风险；
- 是否建议开启下一阶段。
