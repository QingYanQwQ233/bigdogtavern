## 1. 设计哲学

BigDogTavern 是**离线 AI RP/RPG 应用**。它不是一个数据管理工具，也不是一个内容展示站 —— 它是玩家与一个由 AI 驱动、由世界卡定义的世界之间的界面。

五条不可协商的前提：

1. **UI 服务于叙事，不是反过来。** 对话正文永远是屏幕上最强的视觉层级。任何 chrome 的视觉强度都不得超过它。
2. **UI 服务于游戏状态。** 玩家要随时知道"我在哪、我有什么、发生了什么"。这些信息的**可见性**优先于任何装饰。
3. **宿主必须中立。** 世界卡可以覆盖视觉。组件不得依赖某一组具体颜色值。
4. **人性化的交互优先于视觉表现。** 一个好看但让人走不出去的面板，是失败品。
5. **可验证优先于可欣赏。** 设计主张必须能落到可测的数字或可复现的路径上。

**反面清单**：不追求"高级感"、"现代感"、"科技感"这类无法验证的目标；不复制 Material Design / Apple HIG 或其他产品的视觉风格。

## 2. 信息架构

层级模型与出口契约的完整定义在 `skills/ui-design-system/references/information-architecture.md`，此处只记原则：

- 区域分 L1–L4 四层，由 `data-ui-level` 标注。**L2 以下必须能原路离开。**
- 出口有三种语义，不可混用：**Up**（回到父级，由层级决定）、**Step**（回到上一步，由路径决定）、**Close**（关闭覆盖层）。
- **出口永不禁用。** 数据未加载、请求失败、列表为空都不构成禁用理由。
- **出口标签由目标反推，不由来源手写。**

**当前已知偏差**：36 个区域中有 14 个尚无出口控件。这不是设计意图，列入待还设计债。

---

## 3. 布局

- **chrome 与 canvas 分层**：应用 chrome（侧栏、工具栏、状态条）与世界卡 canvas（对话正文、世界内容）是两层，视觉上必须可区分。
- **主内容优先获得空间**：对话正文吃掉所有剩余宽度。
- **列表 + 详情**是基本骨架，三档断点下形态不同但结构一致（见 §9）。
- **侧栏宽度固定，内容宽度弹性。**

---

## 4. 间距

**尺度定义不在此处重复** —— 见 `AGENTS.md §5`，由 `scripts/check_design_scales.js` 守卫。原则：

- 基数是 **2px**，不是 8px。
- **组内间距必须小于组间间距**，这是分组的唯一可靠信号。
- 竖向节奏优先用 `padding` 而不是 `margin`。

---

## 5. 字体

**刻度与角色定义见 `skills/ui-design-system/references/typography.md`。** 原则：

- **离线约束**：只能用系统字体栈，禁止外链字体。
- **对话正文的行高优先于紧凑度**（1.6–1.8）。
- **移动端表单控件字号不得低于 16px** —— 这防的是 WebView 聚焦自动缩放，不是审美问题。
- 代码 / JSON / 正则 / 提示词面必须用等宽字体。

---

## 6. 颜色

**主题 token 与安全校验见 `docs/ui-beauty-declaration.md §4`。** 原则：

- 只依赖**角色关系**（背景 → 面板 → 文字；accent 是全页唯一强调），不依赖具体值。
- **accent 是稀缺资源**：一屏出现两个 accent 元素，其中一个必然应该是次要样式。
- 语义状态不得只靠颜色传达。
- 世界卡可覆盖主题 —— 因此文字颜色必须继承 token，不能写死。

---

## 7. 组件

**角色 / 尺寸 / 状态矩阵见 `skills/ui-design-system/references/components.md`。** 原则：

- 组件 = 角色 × 尺寸 × 状态，三个维度正交，不互相耦合。
- **状态矩阵必须填满**：default / hover / focus-visible / active / disabled / loading / empty / error。
- 判据是行为不是外观：改变状态用 `button`，跳转用 `a`。**本项目当前没有视图级 URL，所以一律用 `button` 是正确的**；将来若引入视图路由应迁移为 `a`，该判断写入 ADR 防随意改动。
- **已知债**：现存 8 套按钮 class、尺寸不统一。策略是**先立规则、阻止增量、不做无收益大迁移**。

---

## 8. 交互

- **每个界面只有一个主操作。**
- **能用内联展开就不要弹窗。** 读对话时被打断的代价高于多一次点击。
- **Escape 永远能退出当前层**，且按最上层优先。
- **关闭覆盖层后焦点归还给触发者**（排除 `document.body`）。
- **破坏性操作必须可撤销或二次确认**（删存档、删世界卡、覆盖导入）。
- **不做无意义的动效。** 动效只用于引导注意、表达状态变化、维持连续性。

## 9. 响应式

| 断点 | 导航 | 内容 |
|---|---|---|
| ≥ 961 | 常驻侧栏 | 两栏 |
| 641–960 | 抽屉 | 两栏 |
| ≤ 640 | 抽屉 | 单栏切换（list ⇄ detail） |

**断点改变的是行为，不是结构。** 同一个出口在三档里都在同一个逻辑位置，只有点下去之后的落点不同。

---

## 10. 无障碍

**契约本体与验证矩阵见 `docs/ui-beauty-declaration.md §7`。** 原则：

- 语义元素优先，ARIA 是补丁不是首选。
- 键盘必须能走完主流程。
- 焦点必须可见。
- 图标按钮必须有无障碍名称。
- 无障碍约束分三档标注：`[静态]`（随 `run_checks` 自动守）、`[运行时]`（改 UI 后手动测量并给数）、`[未强制]`（有原因，人工确认）。

## 11. RPG UI

RPG 界面要同时承载七类信息，它们不是平级的：

| 类别 | 优先级 | 形态 |
|---|---|---|
| 叙事正文 | 最高 | 大段可读文本，宽行高 |
| 世界状态 | 高 | 常驻次级区域，可折叠 |
| 玩家状态 | 高 | 常驻次级区域 |
| 角色 / 物品 | 中 | 列表 + 详情 |
| 任务 / 事件 | 中 | 列表，带状态标记 |
| 地图 | 中 | 独立覆盖层 |
| 元信息（回合数、时间戳） | 低 | 微型标记 |

规则：

- **状态可以常驻，但不能抢戏。** 用次级层级承载，不要用大色块。
- **数字要可读**：属性点、资源、计数用等宽或表格对齐，不要混在散文里。
- **不做花哨的数值动画。** 数值变化用一次短过渡表达即可。

---

## 12. AI RPG UI

AI 带来的不确定性必须在界面上被显式处理：

- **生成中的四种状态都要设计**：排队 / 流式输出中 / 完成 / 失败可重试。不要只有"等待"。
- **流式输出是内容，不是界面。** 不要把正在生成的文本放在会抖动布局的容器里。
- **失败必须能就地重试**，不要把用户赶回上一步。
- **AI 输出不可信**：长度无上限、语言任意、可能含标记语言。UI 必须假设正文会撑满、会溢出、会包含意外的字符。
- **记忆 / 事件 / 世界书的呈现**不能抢正文层级 —— 它们是"可查阅的"，不是"必须读的"。

---

## 13. 定制

**8 区域 × 4 模式（decorate / replace / append / hide）与 sandbox 扩展的完整定义见 `docs/ui-beauty-declaration.md`。** 原则：

- **世界卡的 UI 是内容，不是应用的一部分。** 它不应该被当成需要与宿主保持一致的界面。
- 但世界卡**不能**破坏宿主的核心操作（导航、输入、出口）。
- 主题值必须过安全校验：禁尖括号、花括号、分号、`url()`。
- sandbox 扩展不提供主页面 DOM、网络、文件系统、API key、`allow-same-origin`。

---

## 14. 设计评审

评审纪律是**证据优先**：

> **宁可不报，也不报没有证据的问题。**

- 每条发现必须过三道闸门：**契约**（有约束力的设计决定或用户可见的直接矛盾）、**运行时**（能证明该值/行为确实到达了目标界面）、**修正**（能说出唯一一个由证据要求的改动）。
- 报告前必须做**证伪**：重新打开引用源，努力推翻它。
- **最多报 3 条**，按置信度、用户影响、影响范围、修正成本排序。
- **已知偏差不算发现。** 已登记的例外（如导航项有意做窄、设置弹窗命中区）除非能证明造成了新的具体问题，否则不重报。
- **必须给数。** "命中区偏小"不是发现，"29 个控件里 27 个低于 44px"才是。
- 完整流程见 `skills/ui-design-system/references/design-review.md`。
