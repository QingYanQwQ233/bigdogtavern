# Tavern RPG 卡模式产品路线图

> 需求来源：`RPG 卡模式项目大纲`（2026-08-13）
>
> 文档职责：把产品需求拆成“项目大纲 → 模块细纲 → 可执行小任务”，并按当前仓库真实完成度标记。
>
> 架构底座与历史实施记录仍见 [world-card-architecture.md](world-card-architecture.md) 和 [world-card-implementation-plan.md](world-card-implementation-plan.md)。本文是后续 RPG 产品功能的主路线图。

> 当前执行：R0 契约冻结已落地；R1 正在实现动态玩家创建与独立存档闭环。GitHub 检索未发现可直接兼容本项目的零依赖实现，因此不引入新依赖。

## 0. 结论

当前项目已经有一套较可靠的**世界卡 / 世界存档底座**，但还不是需求中定义的完整沙盒 RPG：

- 已有：世界卡与存档隔离、地图与图片归档、不可变世界版本、回合 CAS / 幂等提交、NPC 知识边界、临时实体、导入导出、旧 RPG 会话迁移。
- 部分已有：世界编辑器、自由文本行动、Markdown 叙事、NPC 动态状态、背包、任务、状态栏、失败重试。
- 主要缺失：按卡定义的玩家创建、动态能力 / 资源 / 特质、可信判定流程、NPC 主动生活、世界时间与事件、通用冲突、成长、分层记忆、失败 / 死亡 / 结局、动态信息 UI。
- 因此，后续不再沿“再补一个底层接口”的顺序推进，而按玩家可感知闭环推进：**建角开局 → 一次可信行动 → NPC 持续反应 → 世界随时间演化 → 系统与成长 → 长期故事与结局 → 平台验收**。

### 状态标记

| 标记 | 含义 |
|---|---|
| ✅ 已验证 | 已有实现，并有当前代码或自动检查证据 |
| 🟡 部分完成 | 只完成数据层、固定版本或部分 UI，尚未形成需求中的闭环 |
| 🧱 仅底座 | 能支撑后续功能，但玩家还不能直接使用该功能 |
| ⬜ 未开始 | 当前代码没有对应的正式能力 |
| ⚠️ 待实机验证 | 静态 / Node 检查通过，但真实浏览器或 Android 尚未验证 |

## 1. 项目大纲

### 1.1 产品定义

RPG 卡不是“只有开场白的角色卡”，而是一个**可运行的世界种子**：

```text
RPG 卡（WorldCard）
  定义世界、规则、玩家创建、NPC、游戏系统、AI 行为与 UI 投影
    ↓ 创建
独立存档（WorldSave）
  保存玩家、时间、世界事实、NPC 状态、地图、记忆与已提交回合
    ↓ 每次行动
观察 → 玩家自由输入 → 行动解析 → 必要时判定 → 世界反馈 → 原子提交 → 新局面
```

AI 同时承担世界模拟器、GM / DM、NPC、叙事者和裁定助手，但不能替玩家决定核心意图。程序负责身份归属、规则边界、随机数、校验、提交与恢复。

### 1.2 十个产品模块

| 编号 | 模块 | 对应原需求 | 当前状态 |
|---|---|---|---|
| M0 | 产品契约与数据所有权 | 项目定位、最终原则、RPG 卡定义 | 🟡 原则清楚，产品契约未版本化 |
| M1 | RPG 卡定义与作者工作台 | 世界准备、RPG 卡应包含什么 | 🟡 仅元数据、地点、NPC、地图可编辑 |
| M2 | 玩家创建、初始关系与开场 | 开局准备、开场生成 | 🟡 已加入声明式 `playerCreation` 与动态存档输入，AI 开场与更丰富规则待后续阶段 |
| M3 | 回合内核、行动解析与判定 | 核心循环、判定系统、AI 行为原则 | 🟡 有自由输入和原子提交，仍是固定状态 JSON |
| M4 | NPC、关系与认知 | NPC 系统、初始人物关系 | 🟡 有作用域与知识隔离，无目标 / 计划 / 记忆闭环 |
| M5 | 世界时间、事件与目标 | 世界演化、任务与故事 | ⬜ 尚无正式时间轴和世界事件引擎 |

### 1.3 不可违反的产品不变量

1. `WorldCard` 只定义世界种子；一切可变化事实必须写入明确的 `saveId`。
2. 一个存档是一条独立世界线。玩家、NPC、关系、地图、图片、时间、选项、状态、记忆和事件不能跨存档串联。
3. 酒馆仍是 `CharacterCard → ChatSession`；RPG 是 `WorldCard → WorldSave`，两条历史与 Prompt 路径不得互读。
4. 玩家拥有角色。AI 可描述已发生的直接后果，不能替玩家选择核心意图、台词、情感立场或不可逆行动。
5. AI 输出只是候选。只有通过规则校验并成功写入存档的变化才是正式事实。
6. 随机数由程序产生并记录，AI 不能自行宣称掷骰结果。
7. RPG 卡扩展必须是声明式 JSON；导入的 HTML、JavaScript、EJS、MVU 或脚本默认不执行。
8. 默认数据继续来自 `_defaults.json`，不能把世界内容、属性名、资源名、规则或 UI 栏目写死在前端。
9. 选项只是建议，自由文本输入始终可用，且不能被选项范围限制。
10. 失败必须生成新局面；是否永久死亡、重伤、俘虏或回退由卡规则定义。

## 2. 模块细纲

### M0. 产品契约与数据所有权

**目标**：明确卡、存档、回合、事实、事件、记忆和 UI 的唯一 owner，避免 AI 文本或全局变量成为事实来源。

**现状**：`worldId + worldVersion`、`saveId + revision`、`charId + kind` 已建立；回合具备 `commandId`、receipt、CAS 和原子写入。世界模式仍把固定 `rpgState` 映射成 HP / MP 等字段，缺少版本化玩法契约。

**细分能力**：

- `WorldCard.schemaVersion`：卡结构版本与迁移规则。
- `turnContractVersion`：行动解析、判定、状态候选、事件和建议选项的输出契约。
- `EntityRef`：世界实体与存档生成实体的稳定 ID 规则。
- `CommittedFact`：只有成功提交的状态变化、事件和消息可进入记忆。
- `Projection`：UI 只读取存档投影，不直接从叙事文本猜状态。

**完成定义**：任一界面字段都能追溯到卡定义或当前存档；任一 AI 失败、解析失败或保存失败都不会制造半提交事实。

### M1. RPG 卡定义与作者工作台

**目标**：作者可用 JSON 和可视化工作台定义一个完整世界种子，而不是只能编辑简介、地点和 NPC。

**现状**：世界草稿支持元数据、世界书 ID、地点、NPC 和地图参数；发布形成不可变版本；世界包可导入导出。尚无玩家创建规则、动态属性、资源、特质、派系、物品、事件、冲突、成长、死亡、结局和 UI 定义。

**卡内模块**：

- `setting`：历史、地理、国家、城市、种族、宗教、文化、科技 / 魔法、社会、经济、法律和当前局势。
- `rules.hard / rules.soft`：硬规则进入校验与裁定，软规则进入 AI 行为约束。
- `playerCreation`：身份字段、属性、点数、范围、技能、天赋、资源和初始关系。
- `entities`：NPC、派系、地点、物品、事件模板和目标模板。
- `systems`：判定、时间、冲突、成长、经济、死亡与结局规则。
- `storyControl`：开场约束、禁用的强制剧情、失败推进方式和结局条件。
- `aiProfile`：身份、玩家主权、知识范围、公平性和输出契约。
- `ui`：声明式分组、字段可见性、顺序和格式，不携带可执行代码。

**完成定义**：换一张卡即可得到不同字段、资源、判定和 UI；前端不需要为“魔力 / 理智 / 赛博义体 / 声望”等题材字段改代码。

### M2. 玩家创建、初始关系与开场

**目标**：玩家按卡作者定义的规则创建角色，经校验后生成只属于该存档的角色快照，再由世界与角色共同生成开场局面。

**现状**：服务端已支持声明式 `playerCreation` 校验，并把用户输入规范化为存档内 `player.snapshot` 与 `state.player`；前端动态建角向导、初始关系输入和 AI 开场幂等提交已接入。互斥条件和更丰富的技能规则留到后续阶段。

**细分流程**：

1. 读取卡的 `playerCreation`，渲染动态身份、属性、技能、特质和资源字段。
2. 实时显示点数预算、互斥条件、范围和必填错误。
3. 玩家确认后由服务端校验，生成不可被其他存档改写的 `player.snapshot`。
4. 初始化 NPC 双向关系、初始地点、时间、资源、物品和已知事实。
5. AI 根据世界当前局势、玩家身份和开场规则生成开场候选。
6. 开场通过协议校验并提交为 revision 1；失败可重试，不污染存档。

**完成定义**：同一世界创建两份不同角色存档，建角字段、开场、关系和状态各自恢复且互不影响。

### M3. 回合内核、行动解析与判定

**目标**：真正实现“观察 → 自由行动 → 解析 → 必要时判定 → 反馈 → 状态提交”的可信循环。

**现状**：自由文本、建议选项、Markdown、流式草稿、严格存档提交和失败重试已有；`DICE_RE` 仍从文本识别骰子并立即随机，判定依据和结果等级没有正式结构，核心状态字段写死。

**目标回合阶段**：

```text
PlayerCommand
  → ActionIntent（行为 / 目标 / 方法 / 风险）
  → CheckProposal（无判定，或属性 / 技能 / 难度 / 因素）
  → ProgramRoll（程序产生并记录随机数）
  → ResolutionCandidate（六级结果 + 叙事 + 状态差异 + 事件）
  → Validate
  → Commit(saveId, expectedRevision, commandId)
  → UI / Memory projections
```

**判定要求**：

- 没有不确定性或结果差异无意义时不掷骰。
- 判定因素可引用属性、技能、特质、装备、环境、NPC、难度、状态与随机数。
- 标准结果支持：大成功、成功、有代价的成功、部分成功、失败、严重失败。
- 判定依据对玩家给出简短可解释摘要，不暴露隐藏推理。
- 解析 / 模型 / 网络 / 校验 / CAS 失败时 revision 不变，并提供明确恢复动作。

**完成定义**：完成一次无需判定行动和一次需要判定行动；重试不重复奖励；篡改未知实体或越界数值被拒绝。

### M4. NPC、关系与认知

**目标**：NPC 是有持续目标和有限认知的角色，不是玩家的功能按钮，也不共享全知视角。

**现状**：世界 NPC、存档 NPC 状态、队伍、当前地点 / 任务作用域、秘密解锁、临时 NPC 和晋升已有底座；关系只是任意对象，缺少正式维度、记忆、计划、主动行为和 UI。

**NPC 定义**：身份、外形、性格、说话方式、欲望、恐惧、利益、秘密、公开目标、长期目标、关系倾向和活动范围。

**NPC 存档状态**：当前位置、状态、双向关系、已知事实、个人记忆、当前目标、计划、承诺、敌意、资源与最近活动。

**运行规则**：

- 只注入当前场景、队伍、相关目标或近期事件涉及的 NPC。
- NPC 只能使用公开资料和自己在该存档中已知的事实。
- NPC 主动行为在已提交的时间推进点结算，不需要后台常驻进程。
- 关系是双向且可不对称的；数值变化必须伴随可说明的事件。

**完成定义**：NPC 离场后仍保持自己的目标和记忆；同一 NPC 在两个存档中的位置、关系和知识完全独立。

### M5. 世界时间、事件与目标

**目标**：世界在玩家行动之间保持连续，并在时间推进时发生与玩家无关的变化。

**现状**：只有消息时间戳和更新时间，没有游戏内时钟、行动耗时、调度事件、世界新闻或历史事实账本；任务仍是固定列表。

**细分能力**：

- `worldClock`：历法、当前时间、时区 / 地区和显示格式。
- `timeCost`：移动、休息、制作、冲突和长行动消耗时间。
- `scheduledEvents`：明确时间或条件触发的事件。
- `worldEvents`：已发生事件、参与者、地点、公开程度、后果和来源 revision。
- `goals / leads`：条件、行动者、动机、时限和当前状态，不锁定 A→B→C 流程。
- `offscreenChanges`：只在提交边界按规则结算相关 NPC / 派系，不做真实时间后台模拟。

**完成定义**：玩家忽略一个带时限目标后，时间推进触发合理后果；重开存档后时间、事件与后果一致。

### M6. 冲突、资源与成长

**目标**：用同一套可配置框架处理战斗、谈判、潜行、追逐、审讯、黑客、政治和商业等冲突。

**现状**：固定 HP、MP、EXP、等级、金币、buff、背包和任务；卡无法定义其他资源或冲突流程。

**声明式系统**：

- `attributes / skills / traits`：显示名、类型、范围、默认值、派生关系和用途说明。
- `resources`：当前值、上限、恢复、耗尽后果和可见性。
- `checks`：骰制、难度、修正、优势 / 劣势与结果梯度。
- `conflicts`：参与者、目标、轮次 / 阶段、可用行动、退出条件与后果；不强制所有冲突回合制。
- `inventory / economy`：物品定义、数量、装备位、货币、负重或题材自定义约束。
- `growth`：训练、学习、探索、关系、事件和冲突带来的能力、身份、声望或资源变化。

**完成定义**：至少用同一内核跑通一个战斗冲突和一个非战斗冲突；成长结果写入人物经历和世界关系，而非只显示“等级 +1”。

### M7. 状态、记忆与上下文

**目标**：长线游戏能记住重要事实，又不把全部历史、全部 NPC 和全部世界书塞进每次请求。

**现状**：已提交时间线、玩家状态、NPC 状态、世界书触发和全局手工记忆存在；没有存档级短期记忆、长期事件记忆、稳定事实、摘要来源和重建机制。

**四层结构**：

1. `turns`：原始已提交历史，永远是来源证据。
2. `recentContext`：最近回合和当前场景，按窗口构建，不作为独立事实 owner。
3. `eventMemory`：从已提交事件提取的长期记忆，带实体、地点、时间和来源 revision。
4. `stableFacts`：世界长期成立或已被正式改变的事实；世界卡原始设定与存档变更分开保存。

**完成定义**：超过上下文窗口后，NPC 仍能正确引用关键承诺；删除派生摘要并重建不会改变正式事实。

### M8. 叙事界面与信息投影

**目标**：正文保持连续叙事，规则信息以可验证的独立 UI 展示，并且界面由卡的声明式定义驱动。

**现状**：RPG 正文支持 Markdown，无酒馆气泡正则；有固定角色 / 背包 / 任务 / 地图 / HP / MP / EXP / 金币界面和独立调试窗口。

**目标界面**：

- 中央叙事：已提交、生成中、失败草稿和待重试状态明确区分。
- 行动区：自由输入始终是主入口，建议行动是可选快捷方式。
- 判定卡：显示使用的能力、主要修正、随机数、难度和结果等级。
- 动态状态：按卡定义分组展示属性、资源、特质、装备、效果与关系。
- 世界投影：时间、地点、地图、事件、目标、NPC 和派系变化。
- 调试窗口：显示实际 Prompt、原始输出、解析结果、候选差异和提交结果，并默认脱敏。

**完成定义**：更换到使用不同属性 / 资源的测试卡后，UI 无需改代码即可正确显示；键盘、窄屏、焦点和 reduced-motion 可用。

### M9. 存档、失败、结局与平台

**目标**：让完整世界线可以安全创建、继续、失败、结束、导出和跨平台恢复。

**现状**：Web 存档支持创建、打开、版本升级、导入导出、迁移、原子写入和恢复；删除 / 复制 / 分支 / 总结未做；Android 内嵌服务器仍只有旧数据 API。

**细分能力**：

- 存档操作：重命名、复制、导出、显式删除和损坏恢复。
- 失败模式：继续、重伤、俘虏、资源损失、永久死亡或卡定义流程。
- 结局：玩家主动结束、规则条件触发或开放式继续。
- 世界线总结：只读取已提交事件与事实，生成可追溯的经历、关系和世界变化摘要。
- 平台：Web / PWA 先稳定，Android 在 API 契约冻结后补齐。

**完成定义**：完整跑通“建角 → 开场 → 多回合 → 失败分支 → 结束 → 总结 → 重开查看”；Web 与 Android 使用同一数据语义。

## 3. 小任务拆分

任务按纵向可玩切片排序。每个阶段都必须同时包含最小的数据、规则、UI 和恢复验证，不先铺一整套永远用不到的抽象。

### B0. 已有底座盘点

| ID | 小任务 | 状态 | 验收证据 |
|---|---|---|---|
| B0.1 | 固定 Tavern 与 RPG 的 owner 边界 | ✅ | `charId + kind` 与 `WorldCard → WorldSave` 分流检查通过 |
| B0.2 | 地图数据、网格和美化图归属存档 | ✅ | `check_session_binding`、`check_world_storage` 通过 |
| B0.3 | 建立世界存档 revision、原子写入和 CAS | ✅ | 过期 revision 返回 409 |

## 4. 实施顺序与阶段门

```text
B0 已有底座
  ↓
R0 产品契约
  ↓
R1 建角并开局
  ↓
R2 可信的一回合
  ↓
R3 NPC 持续性
  ↓
R4 时间 / 事件 / 开放目标
  ↓
R5 冲突 / 资源 / 成长
  ↓
R6 记忆 / 失败 / 结局
  ↓
R7 作者工作台与动态 UI
  ↓
R8 平台与发布验收
```

每个阶段只有同时满足以下条件才进入下一阶段：

1. 玩家可以从入口完成该阶段的可见结果，不依赖手改 JSON。
2. 所有新动态数据有明确 `saveId` owner，切换世界和存档不串数据。
3. 网络、模型、解析、校验、保存失败都有明确恢复路径，且不产生半提交状态。
4. Node 最小回归通过；涉及页面时必须补真实浏览器验证。
5. 开工前完成针对该切片的 GitHub / 官方资料检索，记录许可证和“不重复造轮子”结论。
