# 设计评审

## 第一原则：宁可不报，也不报没有证据的问题

> **Prefer no finding to an unsupported one.**
>
> 重复出现不是问题，实现差异不是问题，视觉印象不是问题。它们只是**候选**。

这条来自 `improve-ui`（MIT，Julien Thibeaut）的证据纪律，本项目全盘采纳。原因很实际：一次没有证据的"改进建议"会消耗一次真实的返工。

## 证据链

每条发现必须能写出完整的五段：

```
角色 → 值 → 来源 → 作用域 → 复现度 → 置信度
```

写不出来就不要写。

## 三道闸门（全过才算发现）

| 闸门 | 要求 |
|---|---|
| **契约** | 能引用一条**有约束力**的设计决定，或同一任务内用户可见呈现的直接矛盾。"倾向于"、"一般来说"、命名相似、重复出现、缺少例外 —— 都不构成契约 |
| **运行时** | 能证明被引用的 owner / 值 / 行为**确实到达了**目标界面。不要跨所有权层或跨生命周期比较 |
| **修正** | 能说出**一个**由证据要求的改动。如果修正方案依赖已有 token / 变体 / 先例，必须点名；如果证据无法确定正确答案、存在多个方案、或需要发明产品意图 —— 驳回 |

**注意**：源码能证明 token、字体、颜色、间距、布局、文案、组件变体、响应式呈现和明确的设计契约违例。**源码不能**把功能行为、状态管理、交互正确性变成设计发现。层级、显著度、密度、清晰度、可发现性、可用性需要**渲染证据或用户证据**。

## 证伪环节

报告前，把每条候选重新打开引用源，努力**推翻**它。出现下列任一情况就删掉：

- 问题和被引用的实现不完全对应
- 规则并不管辖那个属性和界面
- 反证表明该差异是合理或有意的
- 证据支持多个不同修正
- 修正需要发明产品意图
- 另一条发现描述了同一个根因

## 输出格式

按置信度、用户影响、影响范围、修正成本排序，**最多报 3 条**。

```
## 设计语言
- 审计对象：
- 设计来源：
- 已记录的决策：
- 管辖 owner 与消费者：
- 明确例外：（没有引用到明确例外时写"无记录"）

## 发现
| # | 问题 | 证据（契约 / 运行时） | 修正 | 置信度 |

## 先改哪个
（一条，说明为什么）

## 选中项的实施方案
（自包含：执行者没有本次审计的上下文）
```

## 本项目的特殊规则

- **报告只读。** 审计阶段不改产品源码。要写计划就写到独立目录，不要边审边改。
- **已知偏差不算发现。** `docs/ui-beauty-declaration.md §7` 的「当前已知偏差」表和 `nav-item` 窄高度都是登记在案的有意决定。除非能证明它们造成了新的具体问题，否则不要重新报。
- **必须给数。** "命中区偏小"不是发现；"设置弹窗 29 个控件里 27 个高度低于 44px"才是。
- **改动必须可回滚。** 每条修正方案要说明受影响范围。

## 可以做，但不要混淆

- **可用性测试** —— 需要真实用户，不能靠读代码得出
- **审美判断** —— 可以给，但必须标注为偏好而非缺陷
- **架构建议** —— 属于工程评审，不要混进设计评审

## 评审清单

- [ ] 每条发现都有契约引用吗？
- [ ] 有运行时证据吗（还是只有源码猜测）？
- [ ] 通过了证伪环节吗？
- [ ] 修正方案是唯一解吗？依赖已有 token 吗？
- [ ] 报了几条？超过 3 条说明没做筛选。
- [ ] 有没有把已登记的偏差当成新问题？
