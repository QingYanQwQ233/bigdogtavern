# 组件规范

## 组件的三个正交维度

组件 = **角色（role）× 尺寸（size）× 状态（state）**。三个维度不可以互相耦合：不要因为"它是次要的"就顺手改尺寸，不要因为"它小"就跳过状态定义。

### 角色

| 角色 | 用途 | 一屏数量 |
|---|---|---|
| `primary` | 界面里**唯一**的主操作（保存 / 发送 / 确认） | 1 |
| `ghost` | 次要操作、工具栏、**返回出口** | 不定 |
| `tab` | 面板内的并列切换 | 2–7 |
| `nav-item` | 侧栏 / 抽屉的导航项 | 5–7（Miller） |
| `chip` | 标记、筛选、多选 | 不定 |

**判据是行为，不是外观**：会改变状态的是 button，会跳转的是 link。本项目目前**没有视图级 URL**，所以一律用 `button` 是正确选择。若将来引入视图路由（如 `#/chars`），应迁移为 `a` 并保留同样的样式角色 —— 这个判断要写进 ADR，防止以后随意改动。

### 尺寸

只有 `sm` 和 `md` 两档，不要为单个界面发明第三档。

| 尺寸 | 典型高度 | 场景 |
|---|---|---|
| `sm` | 28–32 | 列表内操作、工具条 |
| `md` | 36–44 | 主操作、表单提交 |

**导航项是明确例外**：侧栏 / 抽屉的 `nav-item` 被有意做窄（约 33–36px），这是产品决定，不算债，不要"顺手修好"。

### 状态矩阵（必须全部定义）

| 状态 | 要求 |
|---|---|
| default | —— |
| hover | 仅在指针设备上生效 |
| focus-visible | **必须可见**，不可 `outline: none` 而无替代 |
| active | 按下反馈 |
| disabled | 降低对比 + 不可聚焦；**出口例外，见下** |
| loading | 保持宽度不跳动，给出进度 |
| empty | 说明为什么空 + 下一步能做什么 |
| error | 说明哪里错 / 为什么 / 怎么修 |

## 三条硬规则

1. **出口永远不禁用。** "数据没加载完"不是禁用返回按钮的理由。禁用出口 = 把用户关在页面里。
2. **图标按钮必须有无障碍名称。** 用可见文字最好；不行就 `aria-label`。一个只有符号的按钮对屏幕阅读器是不存在的。
3. **禁用态用原生 `disabled`。** 不要只靠 CSS 变灰——那样键盘用户仍然能聚焦并触发它。

## 已知债（不要顺手改）

现存 **8 套按钮 class**（`ghost-btn` / `btn` / `nav-item` / `st-tab` / `debug-tab` / `seal` / 两套 chip），尺寸也不统一（44 / 36 / 33 / 32 / 28 / 26 / 24）。

处理策略是**先立规则、阻止增量、不做无收益大迁移**：`ghost-btn` 有 147 处引用，全量迁移是高回归风险，而且视觉层即将更换，现在迁移会白做两遍。

**新组件一律按上面的角色 + 尺寸表设计。**

## 组件规格的输出格式

设计一个新组件时给出：

1. 它解决什么问题（一句话）
2. 归属角色与尺寸
3. 结构（DOM 层级 + 语义元素选择）
4. 状态矩阵（上表逐项）
5. token 引用（只引用已有 token）
6. 键盘行为（Tab 顺序、Enter / Space / Escape）
7. 响应式行为（三档断点）
8. 无障碍检查清单

**不要输出 Tailwind 类名** —— 本项目是手写 CSS。

## 评审清单

- [ ] 这一屏有几个 `primary`？超过 1 个就是缺陷。
- [ ] 状态矩阵填满了吗？空/错/加载三态都定义了吗？
- [ ] focus-visible 可见吗？
- [ ] 图标按钮有名字吗？
- [ ] 有没有新增第 9 套按钮 class？
- [ ] 尺寸用的是现有两档之一吗？
